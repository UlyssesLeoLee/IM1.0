# ソフトウェア開発ワークフロー (Software Development Workflow)

> **目的**: 本文档规范 IM1.0 项目从立项到终结的端到端研发流程,涵盖上游策划、要件定义、基本/详细设计、实现、试验(单元 / 集成 / 系统 / 验收)、迁移、发布、运用、保守、品质、项目管理、终结共 16 个 Phase、150 个工程活动。
>
> **适用**: IM Core、Voice Subsystem、Game SDK、Console、Mobile、激光 HUD、运营平台等所有子产品的研发活动。
>
> **约定**:
> - **Phase** = 大阶段(超上流 / 要件定義 / 基本設計 / 詳細設計 / 実装 / 単体 / 結合 / システム / 受入 / 移行 / リリース / 運用 / 保守 / 品質 / 管理 / 終結)。
> - **Activity** = Phase 下的具体工程活动(本文档 No.01–150)。
> - **略称** = 在 PR / Issue / MR / Commit / 会议记录中可直接使用的英文短代码。
> - **GATE** = 阶段出口必须通过评审或基线化,未通过禁止进入下一阶段。

---

## 1. 全流程总览 (Process Map)

```text
超上流 ──→ 要件定義 ──→ 基本設計 ──→ 詳細設計 ──→ 実装 ──→ 単体試験 ──→ 結合試験 ──→ システム試験 ──→ 受入試験 ──→ 移行 ──→ リリース ──→ 運用 ──→ 保守
  01-09      10-21        22-41        42-52       53-58      59-65         66-75          76-89           90-95     96-101   102-108    109-117   118-126
                                                                                                          │
                                                                                                          └──→ 終結 (145-150)
                                                                                                          并行: 品質管理 (127-130) + 管理 (131-144)
```

| # | Phase | 中文 | 目的 | 出口 GATE |
|---|---|---|---|---|
| 01 | 超上流 | 立项前期 | 把业务诉求转化为系统化企画 | PJ 立上げ |
| 02 | 要件定義 | 需求定义 | 明确 What,形成可追溯要件 | 要件 Baseline |
| 03 | 基本設計 | 基本设计 | 设计 How,确定架构 / 界面 / DB / 基建 | BD Review |
| 04 | 詳細設計 | 详细设计 | 把基本设计落到可编码粒度 | DD Review |
| 05 | 実装 | 实现 | 编码、构建、CI | ビルド成功 + CR Pass |
| 06 | 単体試験 | 单元测试 | 验证模块功能 | UT 完了承認 |
| 07 | 結合試験 | 集成测试 | 验证模块间协作 | IT Pass |
| 08 | システム試験 | 系统测试 | 验证非功能 / 端到端 | ST 完了承認 |
| 09 | 受入試験 | 验收测试 | 用户确认业务可用性 | 検収 |
| 10 | 移行 | 迁移 | 把数据 / 流量切到新系统 | 移行結果確認 |
| 11 | リリース | 发布 | 生产部署、上线护航 | Go-Live |
| 12 | 運用 | 运维 | SLA 达成、事件响应 | SLA 持续达成 |
| 13 | 保守 | 维护 | 变更、补丁、修补 | 变更クローズ |
| 14 | 品質管理 | 质量管理 | 全周期 QA | 品质評価 |
| 15 | 管理 | 管理 | 进度 / 风险 / 成本 / 范围 | 持续 |
| 16 | 終結 | 终结 | 收尾、复盘、归档 | プロジェクト完了判定 |

> 14、15 是贯穿全生命周期的并行带,与其他 Phase 并行执行;不作为串行节点。

## 2. 阶段详情 (Activity Catalog)

### 2.1 超上流 (Upstream / 01–09)

经营层把"要做什么"转化为"要做一个什么样的系统"的阶段。本阶段不写代码,只做调研、企画、立项。

| No | 工程 | 略称 | 中文释义 | 主要输入 | 主要输出 | 责任方 |
|---|---|---|---|---|---|---|
| 01 | 経営要求確認 | — | 确认经营层 / 客户的根本诉求与 ROI 假设 | 经营企画书、客户访谈 | 経営要求メモ | PM + 経営層 |
| 02 | システム化構想 | — | 描绘用 IT 解决什么业务问题,提供多套候选构想 | 経営要求、業務課題 | システム化構想書(複数案) | 企画 + PM |
| 03 | システム化計画 | — | 选定一个构想并形成粗粒度路线图 | システム化構想書 | システム化計画書 | PM + 技術リード |
| 04 | 企画 | — | 形成产品企画(范围、价值、KPI、风险) | システム化計画書 | 企画書 / 企画 PRD | PO + PM |
| 05 | プロジェクト立上げ | **PJ立上げ** | 正式组建项目、预算、章程 | 企画書 | プロジェクト憲章 / キックオフ | PMO + 経営 |
| 06 | 現行業務調査 | **As-Is** | 调研现有业务流程(To-Be 对照基准) | 業務ヒアリング、資料 | As-Is 業務フロー | BA |

| 08 | 課題分析 | — | 从 As-Is 抽取痛点、机会点 | As-Is 文書 | 課題一覧 / 改善テーマ | BA + PO |
| 09 | 新業務設計 | **To-Be** | 设计目标态业务流程 | 課題一覧、As-Is | To-Be 業務フロー | BA + 業務側 |

## 4. 命名约定 (Naming Convention)

### 4.1 文档编号

```
{PRODUCT}-{PHASE}-{SEQ}-{TITLE}.md

例:
  IM-REQ-001-UR-Matrix.md          (要件定義阶段的用户要求矩阵)
  IM-BD-003-Architecture.md         (基本设计阶段的架构文档)
  IM-UT-007-Protocol-Test.md        (单元测试阶段的协议测试)
```

### 4.2 分支与提交

```
# 分支
feature/{略称}/{ticket-id}-{short-desc}
例: feature/SR/IM-321-voice-channel-mvp

# Commit
[{略称}] {type}: {desc}
例: [API] feat: add voice channel join endpoint
```

### 4.3 PR / MR 标题

```
[{略称} / Phase-No] {title}
例: [SA / 22] Add voice subsystem architecture diagram
```

### 4.4 Issue 标签

`phase:ur`, `phase:br`, `phase:sr`, `phase:bd`, `phase:dd`, `phase:ut`, `phase:it`, `phase:st`, `phase:uat`, `phase:release`, `gate:rd-review`, `gate:bd-review`, `gate:dd-review`, `gate:go-no-go` 等。
